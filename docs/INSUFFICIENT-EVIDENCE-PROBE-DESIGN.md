# Insufficient-Evidence Model Probe Design

Status: the original dedicated-probe implementation was not deployable because live 404token does not expose its local-only route. The deployment-compatible implementation now calls the existing native account-test endpoint from the Philippines manager. It sends a fixed short text prompt, accepts a result only when the exact candidate appears in `test_start.model` and the stream has a terminal success, and treats model remapping or incomplete streams as ignored evidence. This endpoint can apply `model_mapping` and recover account status after success; it can consume provider quota. Deployment and runtime evidence are recorded in the release section below.

## Goal

For an existing model mapping whose official product evidence is `insufficient_evidence`, query the dedicated 404token account path using the exact mapped ID. If any relevant account returns a complete exact-model success, keep that ID in every affected account mapping. If every relevant account returns a terminal failure, remove it from every affected account mapping. Relevant accounts are active, non-shadow accounts with that exact mapping value. If probing or candidate-specific account screening is inconclusive, skip that candidate and preserve its mappings while continuing with other candidates. Inactive and credential-shadow accounts do not participate in current availability.

## Frozen behavior

1. Candidate IDs are the union of exact upstream IDs referenced by mappings in the eligible account scan whose official status is `insufficient_evidence`. Do not probe IDs already `available` or `unavailable`, and do not probe wildcard rules.
2. Probe candidates only when their complete active/non-shadow mapping scope is known. An incomplete overall inventory leaves all candidates unchanged; a candidate-specific skipped/failed account screen leaves only that candidate unchanged. Other candidates continue. For each eligible candidate, probe every currently active, non-shadow account whose mapping values reference that byte-exact ID, ordered by ascending account ID. Stop probing that ID after the first exact terminal success.
3. Send the candidate through the existing `POST /api/v1/admin/accounts/:id/test` operation with a fixed short text prompt. Because that endpoint may apply `model_mapping`, exact success requires a valid SSE sequence, a `test_start.model` equal to the candidate byte-for-byte, and a terminal `test_complete` with `success=true`. A mapped model, other model, malformed response, or missing terminal event is incomplete evidence, never a failure classification.
4. A terminal SSE `error` is a failed probe only when its structured provider response explicitly identifies a model-level not-found/unsupported condition using an allowlisted model error code. Bare HTTP status, free-form text, account/credential/quota/rate-limit/server errors, unknown codes, and `test_complete.success=false` are incomplete evidence. Transport/admin HTTP errors, malformed SSE, timeout, missing terminal events, or model mismatch are also incomplete. Continue checking other relevant accounts for a possible exact success. If no account succeeds and any result is incomplete, mark this candidate `ignored`, preserve its mapping, and continue screening other candidates.
5. If at least one exact success exists, all account plans retain mappings to the candidate. If every relevant account has a terminal failure and none succeeded, the normalized plans remove all mappings whose upstream value is that candidate. An ignored candidate stays at `insufficient_evidence`; it cannot authorize mapping removal.
6. The approval envelope binds sorted candidate IDs, sorted relevant account IDs, per-account classifications, aggregate outcome (`available`, `unavailable`, or `ignored`), and a canonical digest. Apply re-reads account details for the complete inventory and blocks if the current active/non-shadow exact-mapping participant set differs. Apply never repeats account probes: the approved decision digest binds the screening evidence, while fresh inventory and exact account-scope checks prevent stale-scope deletions without duplicate or potentially billable requests. If a candidate's account scope or relevant catalog screening is incomplete, that candidate is omitted from probe decisions and retains its mapping; other candidates continue.
7. Probe requests use a fixed minimal text prompt, text-only mode, bounded HTTP/SSE bytes and a 30-second deadline. No credential is copied to the manager; requests use the admin API key and server-side account credentials.

## Side effects and operational boundary

The existing account-test endpoint performs real upstream inference and may consume provider quota. A successful test can recover account/rate-limit state; do not describe it as side-effect-free. The manager does not persist response content or raw provider error text. Do not run live candidate probes as part of code tests or local implementation acceptance. Document the quota and account-state effects in the operator guide and admin confirmation.

- API client rejects every probe route outside the exact numeric account path and bounds/validates the SSE protocol.
